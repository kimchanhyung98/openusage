# 새로 고침 및 캐싱

자동·수동 새로 고침의 대상별 주기, 캐시, 요청 제한 정책.

## 데이터가 갱신되는 때

- 활성 프로바이더는 실행 시 한 번 조회 후 일반 사용량 5분, Claude 사용량 15분으로 독립 갱신.
  Claude의 로컬 지출·히스토리도 같은 15분 주기 적용.
  주기는 고정이며 별도 설정 항목 없음.
  팝오버를 열어도 두 번째 자동 순회가 시작되지는 않음.
  프로바이더는 병렬로 조회하므로 빠른 카드가 느린 카드를 기다리지 않고 갱신.
  각 프로바이더 조회는 시스템 잠자기를 제외하고 최대 2분 대기 — 완료 또는 시간 초과로 배치가 끝난 뒤 알림·히스토리 동기화 수행.
  다음 프로바이더 사용량 조회는 대상별 완료 시각부터 기본 간격을 두고 예약.
- 사용량 조회 응답에 포함된 리셋 시각도 사용률과 함께 갱신.
  Codex 타이머 확인·처리 후 별도 조회가 끝나도 다음 5분 사용량 조회는 생략하지 않음.
  그 사이 수동·계정 변경 등으로 새 서버 응답을 받으면 해당 응답의 기존 캐시 유효 기간 적용.
- [Codex 주간 타이머](/docs/providers/codex.md#주간-타이머-자동-시작)는 앱 시작 및 현지 시각 매시 00·15·30·45분에 별도 확인.
  사용량이 0%이면 리셋 시각이 고정돼 있어도 리셋권 사용·시스템 초기화 여부를 계속 확인.
  고정된 리셋 시각이 그대로이면 추가 조회·메시지 생략.
  일반·수동 새로 고침에서도 0% 사용량과 이동하는 리셋 시각을 감지하면 같은 전송 전 검증 진행.
  메시지 준비가 실패하면 다음 수동·자동 새로 고침에서 재시도.
  별도 확인이 진행 중인 조회와 겹치거나 실패하면 해당 계정의 다음 정상 응답으로 이어서 처리.
  전송 전·후의 65초 간격 검증은 한 확인 작업에 포함되며, 5분 사용량 일정과 15분 확인 일정 유지.
- Codex Reset Watch 공개 예측도 별도 15분 주기로 조회하며 프로바이더 새로 고침 배치를 기다리게 하지 않음.
- 프로바이더를 켜면(Customize에서 직접, 또는 첫 실행/신규 프로바이더 감지로 자동) 주기를 기다리지 않고 즉시 조회 — 이미 진행 중인 새로 고침 도중에 변경이 들어와도 마찬가지.
- 대시보드와 설정 푸터에는 다음 일반 갱신까지 남은 시간을 **Next update in …** 한 줄로 표시.
  조회 중에는 **Updating…**, 활성 프로바이더가 없거나 일정이 아직 정해지지 않았으면 **Refresh Now** 표시.
  **이를 클릭하거나(푸터가 보이는 상태에서 ⌘R을 누르면)** 정상 캐시를 건너뛰고 활성 프로바이더를 즉시 새로 고침.
  Claude의 429 재시도 대기는 수동 조회에서도 유지.
  Reset Watch 활성 상태에서는 예측·해당하는 커뮤니티 투표율도 사용량과 함께 재검증하며, 현재 새로 고침 작업이 끝날 때까지 푸터에 **Updating…** 표시.
  연기된 커뮤니티 투표율 조회는 푸터의 갱신 상태를 유지하지 않음 — 해당 조회의 재시도 대기 중에도 수동 새로 고침 종료 가능.
  Reset Watch의 실패·요청 제한 후 재시도 대기는 유지, 이미 진행 중인 요청은 공유하며 별도 자동 주기도 유지.
  커뮤니티 투표율 조회만 실패하면 해당 조회만 연기 — 사용량·예측은 갱신 가능하며 대기 시간이 지난 다음 조회에서 커뮤니티 투표율 갱신 재개.
- 1회 실행 명령 `openusage`는 이 영속 캐시를 일반 사용량 5분·Claude 15분간 재사용하고, 없거나 오래된 항목만 앱을 실행하지 않은 채 새로 고친 뒤 종료.
  `openusage --force`는 캐시 나이와 무관하게 ⌘R과 같은 강제 프로바이더 새로 고침을 실행.
- 프로바이더를 조회하는 동안 이름 옆에 작은 스피너가 나타나고(푸터의 카운트다운 옆에도 하나), 그래서 숫자가 오래된 것인지 헷갈리지 않고 새로 고침이 진행 중임을 알 수 있음.
- 사용량 조회 중 계정 인증 스냅샷·Claude Desktop의 키체인 승인 요청은 앱의 수동 새로 고침 중에만 허용.
  계정·인증 변경 후 자동 조회나 CLI의 캐시 우회는 승인창을 띄우는 수동 요청으로 취급하지 않음.
  계정 인증 스냅샷은 계정 전환·재로그인·Codex 재설정 크레딧 **Use**에서도 승인 허용.
  수동 새로 고침 전에 선택된 Claude 계정의 외부 로그인을 반영할 때도 같은 승인 설정 적용.
  중단된 인증 교체를 복구할 때도 수동 새로 고침·재로그인에서만 저장 로그인 승인 요청 허용.
  수동 새로 고침의 중단된 인증 교체 복구는 승인 응답을 기다리는 동안 화면 응답 유지.
  수동 갱신 중 토큰 재조회·변경 확인·저장에도 같은 승인 설정 유지.
  다른 Keychain 작업이 승인 대기 중이면 최대 5초 대기 후 재시도 안내.
  시작 시 인증 정보 존재 확인은 다른 Keychain 작업을 기다리지 않음.
  등록 계정은 확인 불가만으로 제외하지 않으며, 미등록 로그인의 자동 탐지는 인증 흔적이 확인된 경우에만 채택.
  이미 표시된 macOS 승인창은 사용자가 응답하거나 취소할 때 종료.
- 활성화된 Claude, Codex, Cursor, Copilot 패밀리는 실행 시, 활성화 시, 5분마다, 대시보드 수동 새로 고침 시 공식 공개 상태 컴포넌트도 확인.
  이 확인은 사용량 조회와 분리되어 있어 상태 페이지에 접근할 수 없어도 인증 또는 사용량 오류로 취급하지 않음.
  명시적인 상태 지원이 없는 프로바이더는 상태 요청을 보내지 않음.
- [iCloud 동기화](/docs/icloud-sync.md)가 켜져 있으면 새로 고침 배치는 배치 전체가 끝난 뒤 기기 히스토리 파일 하나를 기록.
  수동 프로바이더 새로 고침은 해당 프로바이더가 끝난 뒤 기록하고, 짧은 간격의 연속 변경은 한 번의 쓰기로 합침.

## 캐싱

스냅샷은 디스크에 캐시돼 실행 시 즉시 로드되므로, 첫 조회가 끝나기 전에도 플레이스홀더 대신 마지막으로 알던 값을 바로 확인 가능.

Claude와 Codex 캐시 항목은 어떤 계정이 만든 값인지까지 기억.
실행 사이에 프로바이더 기본 홈에 로그인된 계정을 바꾸면, 새 로그인 아래에 이전 계정의 한도와 요금제를 잠깐 보여 주는 대신 다음 실행에서 이전 계정의 캐시 값을 폐기(카드는 비어 있는 상태로 시작해 첫 조회로 채움).
앱 실행 중 식별되던 계정을 식별할 수 없게 되면, 같은 계정이 다시 확인되거나 새 조회가 성공할 때까지 이전 캐시 값 숨김.
다른 계정 목록 변경이나 최신 캐시 확인으로는 숨긴 값을 복원하지 않음.
처음 실행하거나 실행 중 Claude 카드를 추가할 때 계정을 식별할 수 없으면 저장된 스냅샷을 숨기고 신원 확인 실패 표시.
계정 목록을 교체할 때도 Claude 계정이 미확인 상태라면 화면에 남은 이전 조회 값 제거.
이때 제거된 카드의 이전 조회 일정도 폐기하고 다음 자동 순회에서 재확인.
재확인 시 프로바이더에 저장된 429 대기는 계속 준수.
Codex의 최초 신원 미확인 시 마지막 값 표시 동작은 유지.

메뉴 막대 앱은 **현재 실행 중 조회한 캐시**만 새로 고침 생략에 사용.
이전 실행의 캐시는 위 계정 확인 조건에 따라 우선 표시하고, 실행 후 첫 순회에서 다시 조회.
Claude의 저장된 429 대기 중에는 첫 순회에서도 사용량 API 조회 보류.
현재 실행 중 조회한 캐시의 유효 기간은 일반 사용량 5분·Claude 15분.
CLI는 실행 이전에 저장된 캐시도 같은 계정 확인 조건과 유효 기간을 충족하면 재사용.

공식 서버 상태는 별도의 5분 캐시를 사용하며 메모리에만 유지.
Claude와 Codex 계정 카드는 계정마다 확인하지 않고 프로바이더 패밀리 결과 하나를 공유.
관련 컴포넌트가 성능 저하, 부분 장애, 중대/전체 장애를 보고하면 서버 해골 표시.
예약된 유지보수와 알 수 없는 결과에는 미표시.
상태 확인 실패는 새 해골을 만들 수 없지만 직전에 확인된 문제 유지 가능.
각 새로 고침 순회에서 마지막 성공 확인으로부터 15분 이상 지난 결과 제거 — 요청 도중 해당 시간이 지나면 별도 타이머가 아닌 다음 순회에서 처리.
정상 해석된 유지보수 전용 결과는 즉시 제거.

Claude, Codex, pi의 지출 히스토리에는 `~/Library/Application Support/OpenUsage/log-scan-cache/` 아래 별도의 로컬 로그 파싱 캐시가 존재.
OpenUsage가 모델 요금 추정을 적용하기 전의 파싱된 사용 이벤트를 저장하므로, 가격이 갱신돼도 변경되지 않은 JSONL을 다시 읽지 않고 반영.
재실행 시에는 경로, 크기, 수정 시각, 파서 버전이 모두 그대로일 때만 항목을 재사용.
같은 홈을 쓰는 카드는 파싱된 데이터를 공유하고, 소스 파일 하나가 바뀌면 그 파일의 레코드만 다시 씀.
pi 로그의 숫자 오류 여부도 캐시에 남겨 재실행 후 같은 손상 행을 정상 빈 이력으로 취급하지 않음.
히스토리 기간이 전진하면 오래된 파일이 캐시에서 빠지고, 35일 동안 쓰이지 않은 identity도 제거.
앱의 쓰기는 새로 고침이 끝날 때까지 모아서 처리하고, 1회 실행 CLI는 종료 전에 대기 중인 쓰기를 모두 비움.

## 가져오기에 실패한 경우

새로 고침 실패 시 기본적으로 마지막 정상 값을 유지하고 프로바이더 이름 옆에 작은 경고 삼각형 표시; 마우스를 올리면 오류 메시지 확인 가능(예: "Not logged in"(로그인되지 않음)).
로컬에서 계정을 확인할 수 없는 Claude 카드는 예외 — 로그인 교체 여부를 확인할 수 없으므로 조회 실패 시 이전 화면 값 제거.
실패한 카드의 계정을 확인하거나 조회에 성공하기 전까지 다른 Mac의 히스토리로 해당 카드를 복원하지 않으며, 제거된 로컬 히스토리는 iCloud 동기화에도 반영.
이 카드는 성공 후에도 화면 캐시만으로 다음 조회를 생략하지 않으며, 인증된 계정의 저장된 429 대기는 계속 준수.
자동 조회는 기존 15분 주기를 유지하며, 수동 조회 성공 후에도 해당 값의 유효 기간이 끝나기 전 재조회 생략.
오류 표시는 다음 새로 고침 성공 또는 앱에서 해당 프로바이더의 API 키 저장·삭제 시 제거.

시스템 잠자기를 제외한 2분 안에 끝나지 않은 프로바이더 조회는 시간 초과 오류로 표시하고 카드 스피너·배치 대기 종료.
시간 초과도 연결 실패로 처리 — 계정의 세션 만료로 판정하지 않으며 마지막 정상 사용량·히스토리 유지.
실패 후 자동 재조회는 60초 동안 보류하며 수동 새로 고침은 이 대기 우회 가능.
다만 취소 요청을 처리하지 못한 이전 조회가 남아 있으면 해당 프로바이더의 중복 조회 보류 — 이전 작업 종료 후 다시 조회 가능.
늦게 도착한 이전 결과는 화면·스냅샷 캐시·Soft Limit 판정에 반영하지 않음.
캐시를 다시 읽는 것만으로 시간 초과 오류를 해제하지 않음.
Reset Credit 사용 후 조회가 시간 초과되면 사용량 조회만 기존 한도 안에서 재시도 — 이미 성공한 Credit 사용 요청을 다시 전송하지 않음.

앱 갱신 작업 취소 시 진행 중인 프로바이더에 취소 요청을 전달하고 배치 대기 종료.
취소된 배치는 완료 시각·히스토리 동기화를 기록하거나 후속 알림 평가를 시작하지 않음.
단, 취소 전에 이미 제거된 로컬 히스토리는 iCloud 동기화에 반영.
제한 시간은 조회 시작부터 계산하며, 조회 시작 직후의 동기 처리 시간도 포함.
2분 제한은 프로바이더 조회 대기에 적용 — 계정 재조정·공개 서버 상태·Reset Watch는 별도 처리.

마지막 정상 정규화 히스토리도 함께 보존되므로, 일시적인 프로바이더 실패 — 또는 로컬 로그 스캔을 잠시 쓸 수 없는 상태에서 성공한 한도 새로 고침 — 가 iCloud 합산 지출 총액에서 이 Mac의 기존 기여분을 지우지 않음.

Claude·Codex·Grok·pi 로그의 토큰 수나 Grok 프로세스 ID가 잘못되었거나 정수로 표현 가능한 로컬 이력 합계 범위를 넘으면 해당 행의 비용·토큰을 함께 제외.
pi 로그에 명시된 비용이 음수·불리언·해석 불가능한 값이면 추정 비용으로 대체하지 않고 손상 행으로 제외; 비용이 없거나 정상적인 0이면 기존처럼 모델 요율로 추정.
비용 객체 자체가 잘못된 형태이면 손상 행으로 제외; 정상 객체에 합계 비용만 없으면 비용 미기록으로 취급해 추정 유지.
재실행 후 디스크 캐시에서 손상 이력을 복원한 경우에도 해당 파일을 처음 사용할 때 진단 기록 — 같은 파일의 반복 조회는 중복 보고하지 않음.
손상된 Codex 누적 집계는 부모 로그 재생 구간에서도 제외.
Codex의 실제 실행 구간에서는 동일 누적값 재전송을 사용량과 모델 상태에 반영하지 않아, 새 턴에서 선택한 모델 유지.
재생 기록 자체가 없거나 누적값이 손상·누락되면 새 정상 누적값으로 기준을 복구하며, 부모·자식 사용량을 구분할 수 없는 증가분은 합산하지 않고 불완전 이력 경고 표시.
Grok의 동일 파일에서 손상 행 수가 늘지 않으면 진단 반복 기록 생략; 정상적으로 읽은 결과에 손상 행이 없어지면 복구 기록 후 새 손상부터 다시 진단.
로그 부재·읽기 실패는 숫자 오류의 복구로 기록하지 않음.
정상 행은 계속 집계하며, 카드에 로컬 이력이 불완전할 수 있다는 안내 표시.
숫자 오류로 유효한 이력을 전혀 만들 수 없으면 마지막 정상 이력 유지; 구독 한도 조회는 계속 진행.

한 번도 데이터가 없던 행에는 꾸며 낸 숫자 대신 "No data"(데이터 없음)를 표시.

## 오래된 데이터

실패한 새로 고침이 마지막 정상 값을 화면에 유지하므로, 새로 고침이 계속 실패하면 그 값이 계속 남을 수 있음 — 프로바이더 쪽에서 바뀐 요금제나 한도가 무한정 옛 숫자로 표시될 수 있다는 뜻.
이를 분명히 드러내기 위해, 마지막 정상 한도 조회 후 일반 사용량 10분·Claude 30분이 지나면 프로바이더 이름 옆에 작은 **"Outdated"**(오래됨) 태그가 나타나고, 마우스를 올리면 정확한 경과 시간을 확인 가능("Last updated 3h ago"(마지막 업데이트: 3시간 전)).
태그는 긴 요금제 이름을 밀어내지 않도록 짧게 유지.
이 태그가 보이면 아래 숫자는 실시간이 아니라 그 시점의 값 — 보통 프로바이더가 새로 고침에 실패하고 있거나(경고 삼각형 확인) Mac이 잠자기 상태였던 경우.
새로 고침이 성공하면 사라짐.

## 대상별 갱신 정책

### 기본 주기

Claude 사용량은 반복적인 HTTP 429에 대응하기 위해 기본 조회 간격을 15분으로 설정.
15분은 OpenUsage의 기본 정책이며 Anthropic이 보장한 안전 간격은 아님.
Anthropic의 서버 제한 정책 변경 여부는 미확인.

| 갱신 대상 | 기본 주기 | 적용 범위 |
| --- | --- | --- |
| Claude 외 프로바이더 사용량 | 5분 | Codex 세션·주간 사용량, Cursor 등 기존 사용량 조회 |
| 공식 공개 서버 상태 | 5분 | Claude를 포함한 기존 지원 패밀리의 상태 확인 |
| Claude 사용량 | 15분 | 구독 한도·추가 사용량과 같은 스냅샷에 포함된 로컬 지출·히스토리 집계 |
| Codex Reset Watch | 15분 | 활성 상태에서 공개 리셋 예측과 관련 커뮤니티 투표율 조회 |
| Codex 주간 리셋 타이머 | 15분 | 활성 Codex 계정의 서버 사용률·리셋 시각 재확인, 타이머 상태 갱신과 조건 충족 시 자동 시작 |

Claude 로컬 로그 집계도 사용량 스냅샷과 함께 15분 주기로 갱신.
Claude의 지출·추이·iCloud에 기록되는 로컬 히스토리에도 같은 자동 갱신 간격 적용.

Codex Reset Watch는 활성 상태에서 15분 주기로 독립 조회.
Codex 주간 리셋 타이머는 공개 예측과 별개인 계정별 서버 확인 작업이며, 같은 15분 갱신 대상에 포함.
앱 시작 시 한 번 확인하고 현지 시각 매시 00·15·30·45분에 확인.
서버 응답의 사용률·리셋 시각을 함께 갱신.
[타이머 자동 시작 조건](/docs/providers/codex.md#주간-타이머-자동-시작)을 충족할 때만 시작 절차 실행.
전송 전·후의 65초 간격 검증, 같은 계정의 중복 전송 방지, 시도 후 5분 보류, 최근 24시간 최대 2회 전송 예약 상한 적용.
15분 타이머 확인·처리 후에도 일반 Codex 사용량의 5분 조회는 유지.
Reset Credit 사용은 별도 사용자 동작이며 주기 갱신만으로 실행하지 않음.

### 자동 갱신 동작

- 5분 갱신과 15분 갱신은 독립적으로 진행.
  Claude 조회가 느려도 일반 사용량과 공개 서버 상태의 다음 순회를 지연시키지 않음.
  같은 15분 그룹에서도 Claude·Reset Watch·Codex 주간 리셋 타이머는 서로의 조회 완료를 기다리지 않음.
- 15분 도래 여부는 5분 순회의 횟수가 아닌 각 작업의 일정으로 판단.
  활성화·수동 조회로 발생한 추가 순회를 15분 도래로 계산하지 않음.
- 일반 사용량·Claude·Reset Watch의 정상 자동 조회는 해당 작업 완료 후 기본 간격을 두고 다음 조회 예약.
  Codex 주간 리셋 타이머는 완료 시각과 무관하게 다음 00·15·30·45분 경계에 예약.
  같은 계정의 타이머 확인은 중복 실행하지 않음.
  오래 걸린 요청 직후 밀린 주기를 따라잡기 위한 연속 요청 금지.
  재시도 대기 시에는 기본 일정과 재시도 허용 시각 중 더 늦은 시각 적용.
- 앱 실행·프로바이더 활성화·새 계정 선택 시 첫 조회는 기본 주기를 기다리지 않고 수행.
  같은 계정의 이미 진행 중인 요청·유효한 캐시·429 대기는 존중.
  Claude 외부 로그인 확인과 계정 목록 재조정은 기존 5분 순회 유지.
  계정 목록만 바뀌고 동일 계정임이 확인되면 Claude 추가 조회나 대기 초기화 없음.
  계정 미확인으로 화면 값을 제거한 카드는 기존 15분 일정을 기다리지 않고 다음 자동 순회에서 재확인하되, 저장된 429 대기 유지.
- 비활성 프로바이더와 비활성 Reset Watch는 예약 조회 중단.
  Codex 주간 리셋 타이머는 활성 Codex 계정만 대상이며 Reset Watch 지표의 표시 여부와 무관하게 확인.
  비활성화·계정 교체 전에 시작한 늦은 결과는 새 화면·캐시·알림에 반영하지 않음.
  재활성화 시 이전 사용량 요청이 남아 있으면 종료 후 갱신 일정 재평가.
  Reset Watch의 조회 진행 표시는 현재 활성화 이후 시작한 작업만 집계.
- 시스템 시계 변경 시 일반·Claude의 로컬 갱신 일정을 새 시각에서 재평가.
  시계 변경 뒤 완료된 조회는 새로 잡은 다음 일정을 유지해 즉시 중복 조회 방지.
  일반 실패의 재시도 대기는 최대 60초로 보정하고, Claude의 저장된 429 대기 종료 시각은 유지.
- 잠자기 복귀 후 기한이 지난 각 대상은 한 번만 조회.
  놓친 횟수만큼 재실행하지 않으며, 저장된 429 대기는 계속 준수.
  팝오버를 열고 닫아도 갱신 주기와 요청 횟수 유지.
- 프로바이더 조회는 시스템 잠자기를 제외하고 최대 2분 대기하며 앱 종료 시 중단.
  시간 초과 뒤 실제 작업이 남아 있으면 같은 대상의 중복 요청 차단.

### 수동 조회와 요청 제한

푸터 클릭·⌘R은 활성화된 두 주기 대상을 모두 새로 고침.
단일 카드 새로 고침은 해당 카드만 대상.
수동 조회는 정상 캐시와 일반 실패 후 60초 대기를 우회할 수 있지만, Claude의 429 대기는 우회하지 않음.
같은 계정의 사용량 조회가 이미 진행 중이면 추가 요청 없이 해당 결과 표시.
Reset Watch 수동 조회의 기존 자동 일정·재시도 대기 정책 유지.
Codex 수동 조회 결과도 기존 주간 타이머 판단에 전달하되, 수동 갱신만으로 메시지를 무조건 전송하지 않음.
타이머 전송 전·후 검증과 전송 상한은 수동 조회에서도 유지.

Claude의 계정 메타데이터에 계정 또는 조직 정보가 없거나 폴백 토큰의 소유자를 알 수 없으면, 해당 토큰의 인증된 프로필에서 계정·조직 신원 확인.
기본 로그인과 저장된 계정도 조직 정보가 없으면 프로필의 계정 일치를 확인한 뒤 조직별 사용량 저장 키 사용.
저장된 계정 UUID 자체가 없으면 복구하지 않으며, 복구한 조직으로 기존 계정 식별자·계정 목록·로컬 메타데이터를 바꾸지 않음.
프로필에서 확인한 계정·조직별로 기존 대기·정상 사용량을 조회하며, 해당 조직의 저장된 대기 중에는 사용량 API 요청 차단.
계정만 같고 조직이 다른 복구 결과는 대기·정상 사용량 기록을 공유하지 않음.
신원 확인용 프로필 요청은 계정별 대기 확인보다 먼저 수행하므로 대기 중에도 발생 가능.
기존에 확인된 계정과 다른 프로필의 인증 정보는 사용하지 않음.
프로필 확인에 실패한 인증 정보로는 사용량 조회 차단; 인증 만료인 경우 다음 후보의 신원을 확인한 뒤 재시도.
프로필 확인 중 로그인 교체 시 이전 결과 폐기 후 현재 로그인 재조회.

Claude의 연속 429 대응은 아래 정책 적용.

| 연속 429 횟수 | 기본 재시도 대기 | 서버 대기 시간이 있는 경우 |
| --- | --- | --- |
| 1회 | 15분 | 기본 대기와 `Retry-After` 중 더 긴 시간 |
| 2회 | 30분 | 기본 대기와 `Retry-After` 중 더 긴 시간 |
| 3회 이상 | 60분 | 기본 대기와 `Retry-After` 중 더 긴 시간 |

`Retry-After`의 초 단위 값과 HTTP 날짜를 처리하고, 없거나 유효하지 않으면 위 기본 대기 적용.
60분은 서버가 지정한 대기 시간의 상한이 아님.
실제 사용량 응답을 정상 해석한 뒤에만 연속 횟수를 초기화하고 정상 15분 주기로 복귀.
캐시 표시·로컬 로그 집계 성공·인증 토큰 갱신만으로는 제한 해제 판정 금지.
429를 인증 만료로 취급하거나 다른 인증 소스로 재시도해 대기를 우회하지 않음.

계정·조직별 재시도 허용 시각·연속 429 횟수는 이 Mac에 보존.
같은 계정·조직은 앱 재시작·토큰 교체·재로그인 후에도 대기 유지.
계정 A의 대기는 계정 B에 적용하지 않으며, A로 돌아오면 기존 대기 복원.
사용량 API 주소가 다르면 같은 계정이어도 저장된 대기·정상 사용량·요청 잠금 분리.
토큰·이메일을 저장 키나 로그에 기록하지 않음.
계정 신원을 확인할 수 없으면 다른 계정의 캐시나 대기를 재사용하지 않고, 확인 실패를 표시·기록.
저장 실패·손상된 대기 상태도 로그와 사용자 오류로 알리고 정상 저장으로 처리하지 않음.
저장에 실패한 새 대기 상태는 재시작이나 다른 프로세스에 전달되지 않을 수 있음.

앱과 1회 실행 CLI는 같은 Claude 계정·조직의 대기 상태를 공유.
동시 실행에서도 요청 직전에 최신 상태를 확인하고 같은 사용량 요청의 중복 전송 차단.
기다리던 요청은 먼저 끝난 조회의 정상 결과·429 대기·일반 실패 결과를 공유.
인증 만료도 같은 인증 정보와 OAuth 갱신 설정으로 기다리던 요청끼리 공유하며, 다른 로그인 정보의 조회는 차단하지 않음.
일반 실패 뒤 새로 시작한 요청은 기존 재시도 정책 적용.
다른 Mac이나 Claude Code 등 외부 프로그램과의 전역 요청량 조정은 보장하지 않음.
재시도 대기 상태는 기기 로컬에 보관하며 기존 iCloud 사용량 히스토리에 포함하지 않음.

### 캐시·오래됨·갱신 표시

| 기준 | 일반 사용량 | Claude 사용량 |
| --- | --- | --- |
| 정상 스냅샷 캐시 유효 기간 | 5분 | 15분 |
| `Outdated` 표시 기준 | 마지막 정상 조회 후 10분 | 마지막 정상 조회 후 30분 |
| 1회 실행 CLI의 캐시 재사용 | 5분 | 15분 |
| 로컬 limits API의 `expiresAt` | 정상 조회 시각 + 5분 | 정상 조회 시각 + 15분 |

앱·CLI·로컬 API의 대상별 캐시 유효 기간 일치.
`expiresAt`·`stale`은 정상 기본 주기로 판정하며, 429로 재시도를 늦췄다고 캐시 유효 기간을 늘리지 않음.
Reset Watch의 공개 예측 보존·부재 판정은 기존 계약 유지.

계정이 확인된 마지막 정상 숫자는 조회 실패·429 대기 중에도 보존하고 실패·제한 안내를 함께 표시.
로컬 계정 미확인 Claude는 조회 실패 시 이전 값 제거; 프로필로 같은 계정을 확인한 429 응답은 저장된 정상 값 유지.
캐시를 다시 표시하거나 로컬 지출만 갱신한 시각을 실제 구독 한도 확인 시각으로 사용하지 않음.
한도의 최신 여부는 실제 마지막 정상 조회 시각을 기준으로 판단.
재시작 시에도 계정이 일치하는 마지막 정상 값은 즉시 표시하되, 저장된 대기 종료 전 사용량 API 조회 금지.
캐시가 없으면 값을 만들어 내지 않고 대기 상태와 데이터 없음 표시.

푸터에는 다음 일반 갱신까지 남은 시간만 한 줄로 안내.
Claude 재시도·Reset Watch·Codex 주간 리셋 타이머의 별도 일정은 푸터에 표시하지 않으며 각 갱신 주기는 유지.
활성 프로바이더가 없거나 일반 갱신 일정이 아직 정해지지 않았으면 `Refresh Now` 표시.
수동 조회의 `Updating…`는 실제 진행 중인 작업에만 적용하며, 재시도 대기 전체를 스피너로 표시하지 않음.
수동 조회나 계정 전환으로 다른 대상의 다음 갱신 시각을 함께 초기화하지 않음.

### 알림·자동 전환·동기화

5분 순회의 시간 경과 알림·일자 전환 평가 유지.
Claude의 새 사용량에 따른 알림·Soft Limit 판단은 실제 15분 조회 결과가 들어올 때 갱신.
캐시·실패·대기 결과는 새로 확인한 사용량으로 취급하지 않음.
현재 자동 계정 전환의 실시간 관측 유효 기간은 일반 표시용 캐시와 분리해 유지.
표시 캐시가 15분간 유효하다는 이유만으로 자동 전환에 쓸 수 있는 관측의 수명을 늘리지 않음.
Claude의 사용량 기반 알림·자동 전환 판단은 새 사용량 조회 결과가 도착할 때까지 늦어질 수 있음.
사용량 초과 방지는 보장하지 않음.

두 갱신 그룹의 정상 결과를 사용량 히스토리와 iCloud에 반영.
15분 그룹 결과도 빠짐없이 저장하되, 실패·취소·계정이 바뀐 결과로 마지막 정상 히스토리를 덮어쓰지 않음.
동시에 끝난 두 그룹으로 일자 전환·알림·히스토리 기여를 중복 기록하지 않음.
