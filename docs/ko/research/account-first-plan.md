# 계정 우선 멀티 계정 계획

Claude/Codex 멀티 계정 지원을 위한 실행 계획입니다. 닫힌 PR #1014
(브랜치 `claude/provider-management-ux-780d96`, 이후 `agent/multi-account-cli-pr1014`에서 진행)를
대체합니다. 이 브랜치들은 **체리픽 자료**로 남겨 둡니다. 인증 스토어 범위 지정, 계정 검색 내부 구현,
스왑 타임라인, iCloud 재매핑, 약 4천 줄의 테스트 대부분을 아래 단계로 옮길 수 있습니다.

> 이 계획의 레코드 모델 위에 **Settings → Accounts**(설정 → 계정)의 관리형 계정 전환이 추가로 구현되었습니다. 현재 동작은 [설정](/docs/ko/settings.md)과 [CLI](/docs/ko/cli.md) 문서가 기준입니다.
> 관리형 계정의 Remove는 OpenUsage의 스냅샷과 작업 공간만 삭제하며, 관리되지 않는 발견 카드는 여전히 아래의 no-Remove 규칙을 따릅니다.

## 재시작 이유

PR #1014는 기본 카드를 *위치*(기본 홈)로, 나머지 계정은 모두 *식별자*로 구분했습니다.
리뷰 결과 거의 모든 높은 우선순위 버그가 이 분리에서 비롯된 것으로 드러났습니다. 기본 카드의 아이덴티티는
변경 가능하기 때문에, 브랜치에는 구조적 결함을 방어하기 위한 약 1.5~2천 줄의 가드 장치
(동일 계정 병합, 중복 억제, 실행 게이팅, 히스토리 보류)가 쌓였습니다 — 그리고 이 가드는 후속
계획에서 다시 삭제될 예정이었습니다. 어느 것도 출시된 적이 없으므로, 단계적
migrate-shadow-flip 절차가 필요한 상태를 가진 사용자도 없습니다. 이 계획은 멀티 계정
디스커버리가 출시되기 **전에** 계정 우선 모델로 전환하여, 그런 가드가 애초에 작성되지 않도록 합니다.

## 목표 모델

모든 카드는 하나의 **계정**입니다. 생성 시점에 발급된 안정적인 레코드 id를 가진 불투명한 아이덴티티
키입니다. 계정이 로그인된 위치는 레코드에 연결된 **소스**(기본 홈, config 디렉터리, cswap 볼트 슬롯,
Desktop/Cowork, Codex 홈)입니다. "Default"는 소스에 붙는 배지(`holdsDefaultSource`)로,
bare id 별칭, CLI 해석, 어트리뷰션에 사용되며 — 절대 키가 아니고 실시간 정렬 순서도 아닙니다.
스왑은 소스 엣지를 다시 가리킬 뿐이며, 카드, 히스토리, 레이아웃, 고정은 절대 이동하지 않습니다.
해석되지 않은 소스는 어떤 계정도 클레임하지 않습니다. 카드는 소스 중 하나 이상이 이 컴퓨터에서
발견되는 동안에만 렌더링됩니다. 모든 소스가 사라지면 카드는 렌더링을 멈추고, 레코드, 레이아웃,
히스토리는 유지되어 로그인이 다시 나타나면 카드가 재연결됩니다(소유자 결정 4 — 아직
Remove 기능 없음).

### 마이그레이션을 없애는 결정

전환 시점에 기본 홈을 차지하고 있는 계정이 **bare id(`claude`, `codex`)를 영구적인 레코드 id로
유지**합니다. id는 불투명하므로 형태 자체에 특별한 의미는 없습니다. 기존 설치는 모두 아무것도
하지 않는 것으로 마이그레이션됩니다. 레이아웃 키, 고정, 히스토리 바인딩, 스냅샷 캐시 항목,
서드파티 API 소비자가 그대로 계속 동작합니다. 나중에 사용자가 기본 홈에서 계정을 스왑하면,
새 계정은 `claude@<hash8>`을 발급받고 기본 배지를 가져가며, 기존 카드는 기존 id 아래에 남습니다.
bare id는 CLI/API 요청에서 패밀리 id 역할도 겸하지만, **별칭 해석은 없습니다**. id는 단순 문자열
매칭(정확한 카드 id, 또는 패밀리 id → 해당 패밀리의 모든 카드)으로 프로바이더를 지정하고,
일치하는 모든 항목이 반환됩니다. 응답은 런타임 상태(어느 로그인이 배지를 보유하는지, 무엇이
활성화되어 있는지)에 절대 의존하지 않으며, 두 API 모두 항상 멀티 프로바이더 형식(limits 응답 객체,
`/v1/usage/:id`에서는 JSON 배열)를 반환합니다.

## 단계

각 단계는 하나의 PR로, **베타 채널**에 출시된 후 다음 단계 시작 전에 충분히 검증(soak)합니다. 문서와
테스트는 해당 슬라이스에 함께 포함됩니다(리포지토리 정책). 예상 소스 LOC는 테스트를 제외한 수치입니다.

### Phase 0 — 독립적 안정성 (모델 변경 없음, ~300 LOC)

- 셸 환경 스냅샷: 느린 로그인 셸에서도 디스커버리 수준의 환경 정보가 유지됩니다
  (체리픽 `22c8e97`).
- 리뷰에 도움이 되는 경우 프로바이더 경계를 따라 파일 분리(`c96fc75`, 필요 시).
- 완료 조건: 실행 안정성 외에 동작 변경이 전혀 없는 베타.

### Phase 1 — 계정 우선 코어, 패밀리당 단일 계정 (~800 LOC)

- `ProviderAccountsStore`(`openusage.providerAccounts.v1`): id, family,
  identityKey, label, sources(+ 배지), tombstone을 가진 계정 레코드. `e052ef9`에서
  이식하되 섀도 비교 절반은 제외 — 레지스트리는 첫날부터 권위 있는 소스입니다.
- Claude와 Codex의 기본 홈 아이덴티티 읽기(검증된 디스커버리 슬라이스 — **아직 후보
  스캔 없음**). 해석된 아이덴티티는 기본 소스를 연결하고, 해석되지 않으면 패밀리는 현재
  상태를 그대로 렌더링합니다.
- 카드는 계정 레코드에서 렌더링됩니다. 패밀리당 계정이 정확히 하나인 경우 현재와 픽셀
  단위로 동일하므로, 구조 전환이 눈에 보이지 않게 출시됩니다.
- CLI + 로컬 HTTP API는 단순 문자열 매칭으로 id에 응답합니다(패밀리 id → 해당 패밀리의 모든 카드, 항상
  멀티 프로바이더 형태; 알 수 없는 id → 404). 의도적인 `/v1` 브레이킹 체인지 하나(`/v1/usage/:id`가
  배열을 반환)를 영원히 별칭을 유지하는 대신 멀티 계정 출시 전인 지금 적용합니다.
- 스냅샷 캐시 아이덴티티 스탬프(v9): 캐시된 값은 자신을 생성한 계정을 기억합니다. 실행 사이에
  스왑이 발생하면 오래된 항목을 새 계정 아래에 표시하는 대신 폐기합니다(`fef9ad0` 이식).
- 완료 조건: 베타 검증; 로그로 실제 환경의 아이덴티티 해석률 확인; 기존 사용자는 아무
  변화도 보지 못함.
- *#1026 + #1027(v0.7.7-beta.1)로 출시됨. 로그아웃 상태 렌더링과 "Remove Account…"(계정
  제거…)는 소유자 결정 4에 따라 완전히 제외되었습니다.*

### Phase 2 — Claude 멀티 계정: config 디렉터리 디스커버리 (~1,200 LOC)

- 후보 스캔(`~`의 점 디렉터리, `~/.config` 아래 디렉터리), 아이덴티티 추출이 곧 검증,
  지원 추적 로그 라인. 디스커버리 내부 구현을 이식하되 병합/억제 배관은 **제외** — 알려진
  계정을 가리키는 후보는 해당 레코드의 또 다른 소스/로그 루트로 연결되므로, 중복 카드는
  구조적으로 불가능합니다.
- 새 계정 → 새 레코드 → 계정 라벨로 이름 붙은 새 카드("Claude — Sunstory"), 대체 이름은
  짧은 해시 id. 사용자 이름 변경은 카드의 컨텍스트 메뉴와 Customize에서 가능합니다. 카드는
  활성화 상태로 시드되고, 레이아웃은 `DefaultLayout.translatedForAccountCards`에서 시드됩니다
  (고정은 절대 시드하지 않음). 카드는 소스 중 하나가 이 컴퓨터에서 계속 발견되는 동안에만
  렌더링됩니다.
- 범위가 지정된 `ClaudeAuthStore`(config 디렉터리별 키체인 이름), 각 홈의 로그에서 계정별 지출 계산.
- iCloud 아이덴티티 라우팅: `PeerHistoryRemapper`, 계정 아이덴티티 매칭, v1 피어 히스토리를
  패밀리 버킷으로 보내 계정 코드(`claude@ab12cd34`)로 이름 붙은 원격 전용 Total Spend
  슬라이스로 렌더링. 두 계정이 존재할 수 있는 순간부터 필요합니다.
- 완료 조건: 실제 멀티 config 디렉터리 사용자로 베타 검증; 라이프사이클 테스트 스위트를 새
  대상으로 재조정하여 통과.
- *#1030으로 출시됨.*

### Phase 2b — 단일 이름 리졸버 (~150 LOC)

- Phase 2의 이름 변경 기능에 대한 후속: 이름 해석에 단일 경계가 없었습니다 — 일부 표면은
  레지스트리에서 변경된 이름을 실시간으로 읽었지만, 다른 표면(Total Spend 범례, 공유
  내보내기, 메뉴 막대 접근성, 알림, CLI/API)은 실행 시점에 `Provider`에 저장된 이름을
  표시하여, 세션 중 이름 변경이 표면마다 다르게 나타났습니다.
- 규칙: `Provider.displayName`은 항상 *파생된* 기본값만 담습니다. 이름 변경은 계정
  레지스트리(`ProviderAccountRecord.resolvedDisplayName`)에만 존재하며 렌더링 시점에
  해석됩니다. 이름 변경은 실행 시점에 이름에 반영해 고정하지 않으며 스냅샷 캐시나 iCloud에도 저장하지 않습니다.
- Total Spend 슬라이스는 호출자가 해석한 제목을 담습니다(라이브 범례와 환경 밖 공유
  렌더가 일치하도록). 메뉴 막대 VoiceOver 텍스트, 할당량 알림, CLI/HTTP API는 각자의
  경계에서 동일한 레지스트리를 통해 해석합니다.

### Phase 3 — Claude: Cowork / Desktop 계정 (~500 LOC)

- 샌드박스별 아이덴티티로 Cowork 샌드박스 탐색. 기존 계정과 일치하는 샌드박스는 해당
  계정의 로그 루트로 연결되고, 별개의 계정은 하나의 Desktop 기반 카드가 됩니다(조직 고정
  아이덴티티, Safe Storage 인증 정보).
- 기존 모델에 새로운 소스 종류를 추가하는 것뿐입니다.

### Phase 4 — Claude: cswap (~500 LOC)

- 볼트 슬롯 디스커버리: 파킹된 각 슬롯은 해당 계정의 소스이며, 활성 슬롯은 기본 배지를
  보유한 계정입니다.
- 스위치 로그 타임라인이 공유 홈의 지출 로그를 계정별로 분할합니다.
- 스왑은 레코드 간 배지 이동일 뿐 — 억제도, 재시작 요구도 없습니다. 프로세스 도중 스왑이
  발생하면 소스를 스테일로 표시하고 다음 실행 때 재조정합니다.

### Phase 5 — Codex 멀티 계정 + 카드별 리셋 (~700 LOC)

- **5a:** 엄격한 아이덴티티 규칙을 적용한 `CODEX_HOME` 후보 스캔 — `tokens.account_id`
  또는 id_token의 ChatGPT 계정 클레임. 자신의 계정을 특정할 수 없는 인증 정보 파일은 절대
  카드가 되지 않습니다(`93e741e` 이식). 범위가 지정된 인증 스토어와 식별자별 로그 루트
  그룹화가 남은 작업입니다. 카드별 `CodexResetClaimRouter`는 관리형 계정 계층과 함께 이미
  반영되어 모든 계정의 행이 첫날부터 자신의 리셋 크레딧을 클레임합니다.
- **5b(필요 시 분리):** 키링 모드 홈 — 검증되지 않은 키링 소스는 실행 후 1회성 계정 스코프
  읽기가 바인딩할 때까지 어떤 계정도 클레임하지 않습니다(`CodexHomeIdentityCache`). 가장
  니치한 슬라이스이며, 5a에서 제외해 5a를 단순하게 유지합니다.

### Phase 6 — 어트리뷰션 다듬기 (소규모)

- Pi 지출 어트리뷰션을 리졸버를 통해 배지 보유자에게 라우팅.
- 패밀리 키 기반 텔레메트리 롤업(`accounts_per_family` 게이지).
- 여전히 필요하다면 Total Spend 패밀리 그룹화/틴팅(이전에 단순 크기 순서가 채택된 이유는
  옛 브랜치의 `c6a63eb` 참조).

## 소유자 결정 (2026-07-19 확정)

1. **첫 번째 계정의 레코드 id로 bare id 사용** — 승인(모든 마이그레이션 제거).
2. 계정에 이메일/조직 이름이 없을 때의 라벨 대체 이름: 짧은 해시 레코드 id
   (`claude@ab12cd34`) — 카드의 컨텍스트 메뉴와 Customize에서 제공되는 사용자 이름 변경과
   함께 제공되어, 보기 싫은 대체 이름도 한 번의 클릭으로 좋은 이름이 됩니다.
3. 새로 발견된 계정은 **활성화** 상태로 시드(PR #1014 동작).
4. **아직 "Remove Account…" 없음.** 이 컴퓨터에서 발견된 계정만 카드로 렌더링됩니다.
   어디에서도 더 이상 발견되지 않는 계정의 카드는 그냥 렌더링을 멈춥니다(레코드, 레이아웃,
   히스토리는 유지되며 로그인이 다시 나타나면 재연결됨). 원치 않는 카드는 기존의 프로바이더별
   비활성화로 처리합니다. 툼스톤은 이후 단계에서 진정한 제거가 필요할 때까지 스키마에만 남습니다.

## 관리형 계정 계층의 릴리스 검증

- `swift build`와 전체 `swift test`를 실행합니다.
